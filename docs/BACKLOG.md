## P0 · 安全：本机进程可以读走全部 Key

> 完整威胁模型、5 个方案对比与一期验收标准见 [SECURITY.md](SECURITY.md)。

**证据**
- CSRF 令牌在进程启动时生成一次，并明文注入首页 HTML（`core/server.py` 的 `_serve_static`）。
- 校验只比对这一个头 + 本机 Origin（`_check_api_auth`）。
- 拿到令牌即可调用 `POST /api/keys/{id}/reveal` 得到明文 Key，或 `GET /api/backup` 下载整库。

**影响**：Host/Origin 校验只挡浏览器跨站与 DNS rebinding，**挡不住本机其它程序**。

**可选方向**（需先做方案对比，不要直接开工）
1. 令牌改为"一次性 + 短时效"，页面加载后由 JS 换取短期票据；
2. 敏感接口（reveal / backup）二次确认，并记录审计；
3. 引入本机回环鉴权（例如命名管道握手），仅允许本进程派生的界面访问；
4. 恢复加密存储（会牺牲"数据可迁移"，属产品决策）。

**验收标准**
- 另一个非本应用进程即使能读首页 HTML，也无法调用 reveal / backup；
- 现有 55 个测试全绿，并新增至少 3 个越权用例。

## P1 · 打包版 `--db` 传绝对路径失败

**证据**（2026-11-05 打包冒烟实测）
- 文件夹版 exe + 默认数据目录 → 正常；
- 文件夹版 exe + `--db rel.db`（相对） → 正常；
- 文件夹版 exe + `--db E:\...\xxx.db`（绝对） → `sqlite3.OperationalError: unable to open database file`；
- 同样的绝对路径用源码版运行 → 正常；
- 最小 frozen 诊断包在**同一绝对路径**建库 → 正常（排除 sqlite 组件与目录权限）。

**影响**：`--db` 未在 README 中出现，只影响开发者手动指定库路径，不影响安装包与普通用户。

**下一步**：在 frozen 环境下打印 `args.db` / `Path(args.db)` / `sqlite3.connect` 的实际入参，确认是参数传递还是路径解析问题。

**验收标准**：打包版用绝对路径 `--db` 能正常建库并启动；补一条覆盖该场景的测试（可用源码模式断言参数解析）。

## P2 · CSS 剩余债务

**现状**（`python tools/check_project.py` 输出）
- 6 个选择器重复定义超过 3 次：`.sidebar`(9)、`.nav-section`(9)、`.nav-item.active`(8)、`.topbar`(6)、`.nav-item`(5)、`.sidebar-foot`(5)；
- 36 个类已定义但 HTML/JS 从不使用。

**为什么没一起做**：这些是**仍在生效的覆盖链**，且 `border-radius` 简写与 `border-top-left-radius` 长写互相覆盖，机械合并会改变最终样式（试过一次，合并结果与层叠结果不一致，已放弃）。5b 只删掉了被 `display:none !important` 永久隐藏的那 21 条。

**建议做法**：按页面切片，一次只收敛一个选择器；每次改完用 A/B 截图 + 像素差异验证（方法见 5a/5b 的提交记录），差异必须落在"同一份 CSS 连拍两张"的噪声区间内。

**验收标准**：`check_project.py` 的重复选择器 WARN 归零；四个页面像素差异为 0（或仅剩动画元素）。
