# 安全边界与加固方案（P0）

> 状态：**2026-11-05 已决策——不实现主密码**。维持"运行本工具的 Windows 账户可信"这一信任模型；
> 明文存储 + 在 CHANGELOG / README / 设置页三处明确告知，作为既定取舍。
> 本文保留，供将来"要对外分发"或"有人要求防本机恶意软件"时直接评估，不必重新调研。
>
> 目标读者：项目维护者。

---

## 1. 当前的信任模型

这个工具的假设是：**运行它的 Windows 账户是可信的**。

已经做了的防护（都有代码依据）：

| 防护 | 位置 | 作用 |
|---|---|---|
| 只监听 `127.0.0.1` | `core/server.py` `start_server` | 不对局域网开放 |
| Host 头校验 | `_check_host` | 防 DNS rebinding |
| Origin 校验 | `_check_api_auth` | 防浏览器跨站请求 |
| CSRF 令牌（每进程一个） | `Application.csrf_token` | 防跨站表单提交 |
| CSP / X-Frame-Options / nosniff / no-store | `_security_headers` | 防注入、防嵌套、防缓存残留 |
| 静态资源路径穿越校验 | `_serve_static` | 防读 `web/` 之外的文件 |
| 打开链接白名单 | `/api/open-url` | 只允许本项目 GitHub Release |
| 备份恢复先备份当前库 | `restore_backup` | 误恢复可回退 |

**没做**的：任何针对"本机其它程序"的隔离。这是本机 localhost Web 应用的共性，不是本项目的独有缺陷。

## 2. 攻击面（按现实可利用性排序）

### A1 · 本机任意进程可读走全部 Key —— 高危，最容易利用

1. 进程 A 请求 `http://127.0.0.1:8765/`，从 HTML 的 `<meta name="csrf-token">` 取到令牌；
2. 带上令牌调用 `POST /api/keys/{id}/reveal` 或 `GET /api/backup`；
3. 得到明文 Key 或整个数据库。

**门槛**：会发一条 HTTP 请求即可，不需要管理员权限。

### A2 · 明文数据库与备份副本 —— 高危，已公开声明

`data/*.db`、`ledger.before-plaintext-*.db`、用户自己导出的备份，全部含明文 Key。
这是 1.3.0 的既定取舍（为了"数据可迁移"），已在 CHANGELOG、设置页、README 三处写明。

### A3 · 剪贴板监听 —— 低

只处理能解析成 Key/.env 的文本，命不中直接丢弃，不落库。但"解析成功"的内容会进内存候选项（10 分钟过期）。

### A4 · 残留副本 —— 中

- 迁移时的 `ledger.before-plaintext-*.db`（加密的，风险低）；
- 恢复备份时的 `ledger.backup-*.db`（**明文**，风险同 A2）；
- `data/app.log`（已确认不含 Key，仅为排障日志）。

### A5 · 浏览器侧 —— 低

DNS rebinding 被 Host 校验挡住；跨站请求被 Origin + 令牌挡住；页面不能被 iframe 嵌套。唯一残余是**本机浏览器扩展**能读页面 DOM，进而拿到令牌——但这已经属于 A1 的同类问题。

## 3. 方案对比

| 方案 | 做法 | 挡住 A1？ | 成本 | 副作用 |
|---|---|---|---|---|
| **1. 短时效令牌 + 会话票据** | 令牌 30 秒过期，页面用 `/api/session` 换票据，票据存内存 | ❌ 挡不住（对方同样能换票） | 低（半天） | 页面切后台久了要重连 |
| **2. 敏感操作二次鉴权** | `reveal` / `backup` / `restore` 前要求输入**主密码**（或 Windows Hello） | ✅ 挡住 | 中（1–2 天） | 多一步操作；忘记密码需重置机制 |
| **3. 本地 IPC + 进程校验** | 服务只接受通过命名管道握手、且 PID 属于本程序派生进程的请求 | ⚠️ 只对桌面窗口模式有效 | 高（3–5 天） | 浏览器模式必须回退到方案 2 |
| **4. 恢复加密存储** | 回到 DPAPI 或主密码派生密钥加密 `secret` 列 | ✅ 挡住"直接读库"（A2） | 中（1–2 天） | 失去"数据可跨机迁移"；需迁移旧库 |
| **5. 只做缓解** | 敏感接口写审计日志、备份文件加权限提示、令牌定期轮换 | ❌ | 很低（2 小时） | 只是"事后可追溯" |

**关键判断**：方案 1 看起来像加固，实际挡不住 A1 —— 因为攻击者能完成同样的握手。不要把它当成解决方案。

## 4. 推荐路线

### 一期（建议先做，收益/成本最高）

**方案 2 的轻量版**：只对三个接口要求二次鉴权 —— `POST /api/keys/{id}/reveal`、`GET /api/backup`、`POST /api/backup/restore`。

- 首次使用时在设置页设置一个**本机主密码**（只存 `scrypt` 派生值 + salt，不存明文）；
- 打开应用后第一次调用这三个接口时弹窗输入，通过后本进程内解锁 30 分钟；
- 忘记密码 → 提供"重置主密码"，但这会**要求当前能解锁数据库**，否则只能放弃数据（需在 UI 写清）。

预估：1–2 天 + 6 个测试（正确密码、错误密码、锁定超时、重置、未设置密码时的行为、审计记录）。

### 二期（可选，视是否需要防本机恶意软件）

方案 4（恢复加密）或方案 3（IPC），二选一：
- 想要"数据可迁移"→ 方案 3，并接受"浏览器模式仍有缺口"；
- 想要"文件被拷走也没用"→ 方案 4，牺牲可迁移性。

### 立即可做的低成本项（可以现在就合）

- 恢复备份产生的 `ledger.backup-*.db` 改名为 `.enc` 或提示用户"这是明文副本"；
- `data/` 目录首次创建时给出"建议限制访问权限"的一次性提示；
- 三个敏感接口写审计行（谁、何时、哪个 Key），复用现有的 `usage_events` 表。

---

## 5. 验收标准（一期）

1. 不输入主密码时，`reveal` / `backup` / `restore` 返回 401 且不返回任何数据；
2. 输入正确密码后 30 分钟内可重复使用，超时后重新要求；
3. 密码错误 5 次后指数退避（防本机暴力破解）；
4. 主密码派生值不落库明文，`scrypt` 参数写在代码里且有注释说明；
5. 新增测试覆盖上述 4 条，且现有 55 个测试保持全绿；
6. `docs/CONVENTIONS.md` 第 7 节同步更新"CSRF 不足以防本机进程"的描述。

---

## 6. 明确不做的

- **不做账号体系**：这是本机单用户工具，没有"登录"概念；
- **不做远程访问**：不开放 `0.0.0.0`，不加 token 给第三方脚本用；
- **不做自动更新下载**：更新只打开 Release 页面。
